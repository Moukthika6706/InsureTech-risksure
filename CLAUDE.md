# CLAUDE.md — RiskSure

## Purpose
Portfolio project for a final-year CS student interviewing at Guidewire (P&C insurance software). RiskSure is a small working P&C policy system for India (INR): Quote → Rating → Underwriting → Bind → Issue, for three products: Personal Auto, Homeowners, Small Business. The full design is in `SPEC.md`; read it before changing the architecture.

The user is new to insurance. Explain insurance terms in plain language and keep design choices explainable in an interview.

## Design ideas (protect these)
1. **Config-driven products**: coverages, base rates, rating tables, modifiers and rules live in `config/*.yaml` (auto, home, business, rules, scorecards). The engine is generic. A new product needs only a new YAML file. Never hardcode rates or product names in Python.
2. **Explainable premium**: the rating engine returns the final premium plus a step-by-step breakdown, shown as a waterfall chart in the UI.
3. **Risk scoring**: Auto uses a gradient boosting model (claim probability 0 to 1) with SHAP top factors. Home and Business use the points scorecard in `config/scorecards.yaml`, which is the single source of truth (read it, never duplicate it).
4. **Underwriting rules engine**: plain, testable Python (no AI). It outputs a decision (auto_approve / approve_adjusted / refer / decline), the adjusted premium and rule hits with reasons. It has a preview function that shows a proposed rule's impact on the sample applicants.
5. **Plain-English rule assistant**: Claude API turns English into rule JSON. The result is validated with a strict schema, the impact is previewed, and nothing is published until the underwriter approves. The AI never prices or decides. Key from `ANTHROPIC_API_KEY`, model from `ANTHROPIC_MODEL`. There are fallback example rules for when the API fails.
6. **Quote lifecycle**: Draft, Quoted, Referred, Declined, Bound, Issued. Transitions are enforced and every change writes an AuditEvent.

7. **Published rules live in the DB** (`PublishedRule` table), merged with `config/rules.yaml` at evaluation time. Render's disk is wiped on redeploy, so the app never writes to YAML at runtime.

## Stack
- Backend: Python 3.12, FastAPI, SQLAlchemy + SQLite, Pydantic, pytest (`backend/app`, `backend/engine`, `backend/ml`, `backend/tests`)
- ML: scikit-learn, joblib, shap. The model is saved to `models/auto_risk.joblib`. Pin exact versions in `requirements.txt`.
- Frontend: React + Vite + Tailwind + Recharts (`frontend/`). Forms are generated from the product config.
- Deploy: backend on Render, frontend on Vercel.

## Data (synthetic, do not edit by hand)
`data/auto_applicants.csv` (5000), `data/home_applicants.csv` (2500), `data/business_applicants.csv` (1500), regenerated by `data/generate_data.py` (seed 42). The README must state honestly that all data and rates are synthetic and illustrative. Auto risk factors are amplified (`AUTO_SIGNAL_STRENGTH = 4`) so the demo model reaches AUC ~0.94; at x1 (realistic noise, like real motor models at AUC 0.60-0.75) the best possible AUC was ~0.70. The README must say this.

## Working rules
- Work one roadmap step at a time. After each step, explain in plain language what was built and how to run and test it, then **stop and wait for "next"**.
- Explain insurance concepts and design choices briefly. If asked "explain this", walk through the code.
- Simple, readable code with short comments. No over-engineering.
- Git commit at the end of every step with a clear message.
- On failure: show the exact error and fix the root cause.
- Ask before big decisions or anything not in the spec.
- Never commit secrets (`.env` is gitignored).

## Roadmap
1. Setup, SPEC.md, CLAUDE.md ✅
2. Hello-world backend + frontend deployed early
3. Auto ML model (AUC, SHAP, save joblib)
4. Product YAMLs + generic rating engine + tests
4b. Rate calibration (`python -m engine.calibrate`, settings in `config/calibration.yaml`): one multiplier per product on coverage rates to hit a 0.65 loss ratio on the sample; factors untouched. Segment loss ratios show the factors don't separate risk enough (young drivers and high/very_high bands run well above target).
4c. Relativity fitting (`python -m engine.fit_relativities [--write --product X]`, settings under `fitting:` in `config/calibration.yaml`): Tweedie GLM per product on the YAML levels, with credibility blending, monotonic ordering and caps. Applied to **home and business only** (user-approved). **Auto deliberately kept as-is**: the x4 data boost makes under-25s cost 20-28x per rupee, so a fit collapses base rates and puts 2/3 of policies on the minimum premium. Young-driver risk is to be handled by Step 5 underwriting rules (load/refer, ML score). The ML score is NOT a price multiplier anywhere.
5. Rules engine + impact preview + tests ✅ — `engine/scorecard.py`, `engine/risk.py`, `engine/rules.py`, `engine/quote.py` (`run_quote`), `engine/preview.py` (`preview_rule`, `book_summary`; `python -m engine.preview`). 12 starter rules in `config/rules.yaml` sized from sample loss ratios. The ML score affects price only through rules (refer very_high, load high +50%).
6. DB models + API (quotes, bind, issue, queue, audit) ✅ — `app/db.py`, `app/models.py`, `app/lifecycle.py` (only place status changes), `app/services.py` (`active_rules` = rules.yaml + DB `PublishedRule`), `app/routes.py`, `app/schemas.py`. Tables created on startup (no migrations). Tests use in-memory SQLite via dependency override. Dashboard and rules endpoints not built yet (Steps 7/8).
